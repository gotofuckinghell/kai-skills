# Stalker Clear Sky Config Modding

How to edit X-Ray engine `.ltx` config files for S.T.A.L.K.E.R. Clear Sky.

## Hard Rules

- **Encoding is cp1251** (Windows Cyrillic), not UTF-8. Read/write with `encoding="cp1251"`.
- **Make a `.bak` before every edit.** `shutil.copy2(path, path + ".bak")`.
- **Diff after editing** to verify only intended lines changed.
- **Section headers can have `:parent` suffix** (e.g. `[exo_outfit]:outfit_base`). Match by `.startswith()` prefix, not exact string.
- **Tab vs space inconsistency** — original files mix both. Preserve whatever the line already uses.
- **Changes take effect on game restart**, not on save-load.
- **gamedata/configs/** overrides **documents/gamedata/configs/** — if the file exists in both, edit the one in `gamedata/configs/`. If it only exists in `documents/`, copy it to `gamedata/configs/` first.

## Key Files

| File | Purpose |
|------|---------|
| `gamedata/configs/misc/outfit.ltx` | Armor stats: protection, sprint_allowed, weight, artifacts |
| `gamedata/configs/misc/stalkers_upgarde_info.ltx` | Mechanics: what items they upgrade, which upgrades are blocked |
| `gamedata/configs/creatures/actor.ltx` | Player movement speed, immunities, condition |
| `fsgame.ltx` (game root) | Paths: `$app_data_root$`, `$game_data$`, `$game_saves$` |

## Russian Display Names (Localization)

UI strings live in `localization/xrussian.db` (~275 MB) — unpack with xrUnpacker64 `-unpack -xdb` (works, same as configs.db). Texts land in `configs/text/rus/st_items_*.xml` — **cp1251**, despite the xml declaring windows-1251. `st_items_outfit.xml` holds armor names/descriptions; xml `id` attributes have NO `st_` prefix and match config `inv_name` values verbatim (`id="exo_outfit_name"` ↔ `inv_name = exo_outfit_name`). Use this to map sections to in-game names (e.g. found: scientific_outfit = «Комбинезон "СЕВА"», svoboda_exo_outfit shows «Экзоскелет "Свобода"» via exo_freedom_outfit_name).

## Trade System (buy/sell/supplies) — verified against xray-15 engine source

**Key files** (all in `gamedata/configs/misc/`): `trade_generic.ltx` (DEFAULT trade file for ALL generic stalkers — set by `xr_logic.script` when a stalker logic has no `trade =` line) and `trade/` dir with 15 per-trader files (`trade_trader_esc.ltx`, `trade_barmen_all.ltx`, ...). Logic files (`configs/scripts/<level>/*.ltx`) map unique NPCs via `trade = misc\trade\trade_xxx.ltx`. `misc/trade_trader.ltx` is NOT referenced by any code — dead file.

**Format**: each file starts `[trader]` with 3 condlist fields: `buy_condition` (what NPC buys from player), `sell_condition` (what NPC sells), `buy_supplies` (his stock sections). Condlists pick ONE section: `{=info_x} secA, {=info_y} secB, secC` → first matching condition wins.

**Section line semantics** (engine `CTradeParameters::process`): `item = F, E` = ENABLE trade with friend/enemy price factors (price = base × condition × interpolated(friend,enemy,goodwill)); `item` with NO value (`ammo_x ;NO TRADE`) = DISABLE (refuse). **Items not mentioned at all are ENABLED at default factor 1** — so refusal happens ONLY via explicit empty-value lines, and unlisted items already sell at full price.

**Supplies lines** = `item = count, probability` (CPurchaseList spawns up to count items each with that probability, restocks ~24h). Traders' spawn sections have `max_item_mass = 10000` so stock weight is not a concern; generic stalkers have normal weight limits.

**Items are untradeable if their own section has `can_trade = false`** (quest PDAs, flash cards, maps, af_compass, dev_flash, `flesh_up_*` trees). This gate is separate from trade-file lists.

**Inheritance**: `[sec]:parent` header form AND `:parent` body-line form both exist; child keys override parents. Beware of GSC's vanilla duplicate keys inside one section (secret trader sell/ammo_pkm_100, bandit buy/medkit) — pre-existing, leave them.

**"Traders buy everything" mod recipe** (applied 2026-09): flip every real-good NO TRADE line in buy-candidate sections to `= F, E` using per-file per-category conventions (most common pair among that file's enabled lines; fallback (1,1) or avg). For trader stocks: append whole-arsenal block (all `wpn_*` + ammo + 14 outfits + grenades, e.g. `= 2, 0.6`) to the ROOT of each supplies-candidate inheritance chain (one add per root covers inheriting candidates). Then ensure every stocked item is sell-enabled in sell candidates (convert its NO TRADE or add with sell convention).

**"Traders sell everything" mod recipe**: full procedure in references/trade-sell-all.md; runnable passes: scripts/trade_sell_all.pl (clear bans in sell sections + fill stock roots) then scripts/trade_sell_all_fix.pl (clear remaining bans in buy sections and supplies chains). Key rules: (1) each trade/*.ltx carries LOCAL trade_generic_buy/sell copies — misc/trade_generic.ltx edits never propagate to named traders, run both; (2) generic stalkers have NO buy_supplies — they sell only from inventory; (3) add stock at the chain ROOT, but a NO TRADE in a CHILD section overrides a root enable — clear bans at every chain level; (4) value conventions: sell `= 1.7, 1.7`, buy `= 0.5, 0.3`, stock `= 3, 1.0`; (5) exclude service wpn sections from any "all items" list (`_minigame`, `_up\d*`, `_hud`, `no_draw_sound`, `with_scope`, `wpn_rpg7_missile` — w_*.ltx has ~93 wpn headers but only ~39 real weapons); (6) `grep NO TRADE` also matches your own `(was NO TRADE)` marker comments — a real leftover ban is a bare key line without `=`; (7) filter the master list to sections with a direct `class =` line — the shipped scripts do this; without it, class-less fx sections (af_activation_*/af_*_absorbation) get stocked and the game FATALs mid-load.

## Installing Big gamedata Patches (SRP and similar)

Big community patches (e.g. Sky Reclamation Project v1.1.4, ModDB `mods/srp`, also `github.com/Decane/SRP`) ship as a full `gamedata/` tree that OVERWRITES every mod file of the same path — your trade edits, character_desc money XML, cheat scripts, actor.ltx. Before installing one:
1. **Snapshot everything** into a folder (user's standing preference — he wants the exact file texts back): copy every gamedata file newer than the game install (`find gamedata -type f -newermt "YYYY-MM-DD"`) preserving paths, PLUS the idempotent re-apply scripts, PLUS a plain-text manifest listing each block, what it changes, and how to re-apply. Reference layout: `Documents\Stalker_mods_backup\` (manifest.txt, gamedata_full_copy/, reapply_scripts/, orig_vanilla/).
2. **Re-apply = scripts on top of the patch's files, not file copies** — copying your old trade/character_desc files back discards the patch's fixes to those files. The stock/money scripts are idempotent (marker-comment based) and safe to run on any baseline, including twice.
3. SRP specifics: gamedata-only (no exe patch in v1.1.4); readme REQUIRES a new game (its scripts/logics change — old saves may not load); it also ships its own trade files, character_desc XML and actor.ltx. Full procedure: references/installing-big-patches.md. Always-on re-apply deltas: (a) money — re-run the boost over the WHOLE `gameplay/character_desc_*.xml` glob, never your remembered file list: the patch ships MORE profile files than you had (SRP: 13 on disk incl. limansk/katacomb/military/stancia_2/generator vs your 8) and overwrites yours; (b) trade — the patch may restructure files into `#include "trade_template.ltx"` whose `[trade_nothing]` is the SHARED parent of every trader's buy AND sell sections and holds the patch's global NO TRADE ban list: clearing bans there (the fix pass reports e.g. "112 in 1 file" = the template) unlocks BOTH directions for all traders at once, and such files may legitimately lack `buy_supplies` (commented) or a `[trader]` header (the template file itself) — scope post-edit assertions accordingly; (c) scripts — probe the patch zip for which scripts it ships BEFORE restoring cheat scripts: SRP ships ui_main_menu/bind_anomaly_zone/sr_no_weapon/modules and NOT zone_no_weapon/god/ui_teleport/anom/ui_si (survivors verify by md5 vs snapshot); restore from snapshot only the script whose patch replacement breaks your entry point (SRP ui_main_menu wires btn_spawn to a ui_spawn_dialog it does NOT ship and drops your hotkeys); hotkey-opened dialogs (main_menu:OnKeyboard DIK_Y/DIK_U) are the robust integration point — db-vanilla ui_mm_main.xml has no btn_spawn element, so button callbacks never fire while hotkeys always do; keep the patch's bind_anomaly_zone/sr_no_weapon (Decane-fixed and paired with patch modules.script); (d) configs the patch rewrote structurally (actor.ltx/outfit.ltx) — transfer values key-by-key from the snapshot into the patch file, never whole-file copy-back; (e) a patch may COMMENT OUT quest-PDA sections in quest_items.ltx (SRP: `;[device_pda_military]`...) or drop them — re-add full clones from the snapshot when saves/tasks can reference them. Verified counts and details: references/installing-big-patches.md.

**Pitfalls**: header inheritance parse regex must be `\[([^\]:]+)\](?::([^\]]+))?$` (parent AFTER closing bracket). Suffix filters must be end-anchored — substring `_mp` wrongly kills `wpn_mp5`. Vanilla `af_rusty_*`, `af_ameba_*`, `af_drops`, `soldier_outfit` have NO defining sections in configs.db (dead CoP leftovers, only in unused trade_trader.ltx). **A hand-applied (manual Explorer-copy) patch install can leave a MIXED tree**: files the patch does not ship keep whatever was on disk — including same-path files pulled from other mod folders — so sibling pairs disagree (outfit.ltx `upgrades =` refs vs outfit_upgrades/o_*.ltx definitions) and the next save load FATALs `Can't open section 'up_gr_*'`. File DATES do NOT diagnose it — patch archives keep original timestamps (SRP ships 2013–2021 dates) and zip extractors preserve them, so patch-overwritten files still look old; a date-based read misjudged 86 upgrade files as user mods when md5 proved they were the patch's. The reliable check is md5 of every on-disk config vs the patch zip: scripts/compare_patch_md5.py (SRP matched 340/365 .ltx). Fix = audit (scripts/audit_upgrade_refs.py) + restore the canonical file from configs.db — never copy the crashing file over from a Desktop mod archive (that is usually the mismatch source).

**"Upgrade limit" symptom (can't install all upgrades on armor/weapon)** — the item's `upgrades =` line in the ITEM section (w_*.ltx / outfit.ltx) is the ONLY list the engine wires up: `inventory_upgrade_root.cpp` `Root::construct` builds the tree from `add_dependent_groups(upgrades_str)` and ignores branches that exist in the tree files (weapons/upgrades/w_*_up.ltx, misc/outfit_upgrades/o_*.ltx) but are not listed. A patch can ship tree files with 2nd-level branches it never connects (SRP: o_exo has 16 up_gr, item lists 5; w_abakan_up has 12, item lists 6) — that is the «limit». Two incompatible tree philosophies: «full upgrades» mods use single-letter sequential branches (up_gr_a..i, then e2/f2...e3: 9–15 per item); vanilla/SRP-style uses combos (up_gr_ab/cd/ef/gh: 4–6). The pair (w_x.ltx + w_x_up.ltx) and (outfit.ltx + o_*.ltx) MUST come from the same source — never mix generations.

**Upgrade generation is SAVE-CRITICAL**: saves store installed upgrades by branch name, and loading runs `Manager::upgrade_verify(item_section, upgrade_id)` (inventory_upgrade_manager.cpp), which VERIFY2-FATALs unless the branch is registered in THAT item's Root tree — the tree built from the item's CURRENT `upgrades =` line. A branch section existing in pSettings is NOT enough. The same `Can't open section 'up_gr_ab_pm'` message therefore also fires when the ITEM file generation changed under a live save (combo-era save + single-letter full-upgrades-mod item file), with the branch text present in the tree file all along — this is how a «limit fix» by wholesale mod swap crashes save load. Fix order: restore the exact file generation the save was made under (`.bak_*` taken from the then-working state, incl. outfit.ltx), THEN make save-safe changes; a full-upgrades swap over a patch-era save means a new game. Adding EXTRA branches to an item's `upgrades =` (2nd-level alternatives already defined in its tree file) IS save-safe — saves only reference what was installed. Armor artefact slots are NOT configurable: `artefact_count` is hard-clamped 0–5 in engine code (CustomOutfit.cpp `clamp(m_artefact_count,0,5)` + UI `UpdateOutfit` VERIFY `af_count <= 5` with a fixed 5-element overlay array) — values >5 are dead on stock binaries, and ТЧ/CoP belt recipes (system.ltx `max_belt`, inventory XML belt rows) must not be transplanted — the CS `m_iMaxBelt` engine path is commented out (Inventory.h), belt size comes only from the outfit `artefact_count`. Artefact effects are belt-only too: damage mitigation (`HitArtefactsOnBelt`, Actor.cpp) and the periodic effect update (`UpdateArtefactsOnBeltAndOutfit`) iterate `m_ArtefactsOnBelt`, which fills only in `OnItemBelt` — artefacts sitting in the rucksack do NOTHING, so «make artefacts work from inventory» is an engine change, never a config one. Also check before launching: `[upgraded_inventory]` (misc/inventory_upgrades.ltx) runs `VERIFY2(section_exist)` for EVERY name at startup (FATAL if any section is missing from pSettings — add clones of missing ones, e.g. wpn_g36_up2 cloned from wpn_g36 with its `upgrades =`, `installed_upgrades` commented out); and every `upgrade_scheme = u*` value must exist as `name="upgrade_scheme_u*"` cells in configs/ui/inventory_upgrade.xml (SetCurScheme VERIFY2 «Scheme does not loaded» — the schemes are UI-XML cells, there are NO upgrade_scheme ltx sections anywhere). Full mechanics + restore procedure: references/upgrade-system.md.

**Quest-item gates (3 independent layers)**: (1) `can_trade = false` in the item's own section; (2) `quest_item = true` — engine `CInventoryItem::CanTrade()` returns false for quest items REGARDLESS of can_trade, and the UI hides the drop option (`PropertiesBoxForDrop` / `DropAllCurrentItem` / kDROP key handler all check `IsQuestItem()`); (3) `;NO TRADE` lines in trade catalogs. To unblock quest junk: set both flags open in `misc/quest_items.ltx` (+ items.ltx/artefacts.ltx for dev_flash/af_compass — copy from db first, they don't exist in gamedata) and flip their NO TRADE lines in BUY sections of all trade files (Sell sections keep them so NPCs won't offer quest items). SP quest sections: device_pda_* (8), esc_trader_habar, af_compass + can_trade-only items (flash cards, maps, agr_mechanic_pda, mil pda, dev_flash_1/2, esc_device_pda_driver). **Save-load crash diagnosis & repair** — a save dies at load when a saved object's section is missing from pSettings (engine re-creates saved objects by section name): FATAL `CInifile::r_section "Can't open section 'X'"` (Xr_ini.cpp:443). Fastest message source: game-root `XRayEngine_error_report_*.zip` → `errorlog.log` (BugTrap report; the xray log itself is overwritten every launch and can be empty after a hard crash). Reproduce/verify from CLI: `bin/xrEngine.exe -load <savename>` (GOG "Launch ...lnk" is the same exe). Two failure moments: (a) at SAVE LOAD (first missing object in the save's object order — iterate, the next missing section surfaces after each fix); (b) mid-GAME when an NPC interaction renders a saved TASK: random "bring item" tasks (CBringItemTask in task_objects.script) store requested item section names in the save; rendering task text does system_ini():r_string(item,'inv_name') → same FATAL when the item came from a removed mod (real case: esc_quest_magic_vodka at «взять квест»). Task item names live in the COMPRESSED part of the .sav — a .sav grep showing 0 hits proves NOTHING (same for any save-resident object).

Fix = append a FULL clone section (header keeping `:parent` chain + complete donor body incl. `class`) of the nearest CS item to `gamedata/configs/misc/quest_items.ltx` (it IS in pSettings, included once from system.ltx). Never DISABLE/remove a clone section once an object with that section may exist in saves (spawned items land in NPC inventories/traders): disabling it breaks every dialog/trade with the owner (engine creates the item to show his inventory → same FATAL). If a clone is broken, FIX it in place (correct parents/upgrades from the live donor), don't take it out. Critical rules: (1) verify the WHOLE parent chain resolves in pSettings — a donor file existing on disk is NOT enough: system.ltx includes only monsters.ltx + stalkers.ltx from creatures/, so m_burer/m_zombie/m_cat/m_fracture/m_chimera .ltx are not loaded and burer_weak/normal, zombie_trup2, bloodsucker_marsh, cat_*, fracture_*, veh_* can NEVER exist in CS — do not clone them (my burer clones crashed load with "Can't open section 'm_burer_e'"); (2) weapon clones must take the `upgrades = up_gr_*_<wpn>` line from the LIVE donor — this user has an upgrade mod rewriting gamedata/configs/weapons/w_*.ltx, so vanilla scheme names (up_gr_ab_pm...) don't resolve and object creation FATALs; when the live donor has no `upgrades` line, remove it from the clone; (3) strict engine reads may demand keys vanilla sections lack — CArtefact::Load strictly r_floats `additional_inventory_weight`, and spawned af_compass (SCRPTART, never a real object in vanilla) lacks it: add `additional_inventory_weight = 0`. Lua FATALs (e.g. `bind_anomaly_zone.script ... attempt to index local 'art' (a nil value)`) = override the script in gamedata/scripts with a nil-guard; delete stale table keys only AFTER the pairs() loop, never inside it. `CPhraseDialog::SayPhrase "No available phrase"` = vanilla bug for saves made during an active dialog — not mod-caused. **`Can't open section 'up_gr_*_<item>'` = missing upgrade-BRANCH sections, not a missing object**: the item's `upgrades =` refs (paired branches up_gr_ab_/cd_/ef_/gh_) have no definitions in the loaded upgrade files because sibling o_*.ltx / w_*_up.ltx come from a different mod generation (single-letter a–g only). ANY item of that type FATALs at save load. Fix = audit refs vs definitions across ALL armor/weapon upgrade files at once (scripts/audit_upgrade_refs.py — catches every broken file, not just the first crashing section) and restore the canonical file from configs.db — never clone the object section, never hand-write branches. Full crash taxonomy, diagnostics and recipes: references/save-crash-repair.md

## Engine Internals: db Content, NPC Money, UI Boundary

- **Mechanic questions are answered by source, not guessing**: clone `OpenXRay/xray-15` (branch `xd_dev`, ~74 MB, sources under `cs/engine/`) and grep — it is the Clear Sky engine. Covers money, trade, UI, spawn; verified answers beat forum lore.
- **Anything missing from `gamedata/` lives in `resources/configs.db`** (gameplay XML, profiles, scripts). Override = extract the FULL file from the db and drop it at the matching `gamedata/configs/...` path. Format, LZHUF catalog decoder build, and extraction: references/db-archive-format.md.
- **NPC money comes from `<specific_character>` profiles** (`gameplay/character_desc_*.xml` in the db): `<money min max infinitive/>`; `infinitive="1"` makes money never decrease. Boost recipe and the trade-UI stack/Ctrl analysis: references/npc-money.md.

## Log Triage (fast, Perl)

Logs: `Documents/Stalker-STCS/logs/xray_administrator.log` — **overwritten every launch**; after a hard crash it can be empty or end mid-line. Crash dumps `.mdmp` accumulate in the same folder (name = timestamp). Game-root `XRayEngine_error_report_*.zip` → `errorlog.log` is the BugTrap report (authoritative for hard crashes). Fresh `.mdmp` timestamps = crash history; none since date X = no crashes since X.

Fast triage: `perl scripts/xray_log_analyzer.pl <log>` (this skill's scripts/ folder). Output: total/unique lines, top repeated noise, FATAL markers, stack frames, unique ERROR/WARNING lines. Interpretation rules:
- Section names containing 'crash' (`[hospital_z2_heli_crash]`) or `[NNNN]=[name_with_warning]` are FALSE positives — the script already filters them.
- Log ending in `RM_Dump:` / `refCount:` blocks = clean engine shutdown (normal exit), NOT a crash.
- Benign stock errors (no action needed): `Renderer doesn't support blender` (R3 shader on modded/new GPU — one effect missing), `Invalid ogg-comment version` (one broken voice line skipped), `attempt to use non-existent INFOPORTION` (mod script references a missing infoportion — classic for item spawners/upgrade mods).
- Real FATAL lines look like: `FATAL: CInifile::r_section "Can't open section 'X'"`, `FATAL: ... stack trace:` — see save-crash-repair.md for taxonomy.

## Common Tasks

### Increase Armor Protection (outfit.ltx)

File: `misc/outfit.ltx`. Protection lives DIRECTLY in the suit section as fractions of 1.0 (UI shows them as %, i.e. value × 100): `burn_protection`, `shock_protection`, `radiation_protection`, `chemical_burn_protection`, `telepatic_protection` (anomaly types, usually 0.03–0.06) and `strike_protection`, `explosion_protection`, `wound_protection`, `fire_wound_protection`, `physic_strike_wound_immunity` (physical, usually 0.25–0.56). Suit display names: `[exo_outfit]` = «Экзоскелет», `[svoboda_exo_outfit]` = «Экзоскелет "Свобода"» (the two top armors), `[scientific_outfit]` = «Комбинезон "СЕВА"» (anomaly/rad suit — players call it просто «Сева»).

Recipe: multiply the ten protection keys by the wanted factor (+50% → ×1.5, +80% → ×1.8). Do NOT touch `bones_koeff_protection` (bone-hit mapping table) and NOT the small `burn_immunity`/`explosion_immunity` etc. in `[sect_*_outfit_immunities]` (≈0.01–0.03 — suit self-degradation coefficients, not player protection) — but `strike_immunity` in those SAME sections IS a real damage multiplier for strike-type hits (falls/collisions/monster blows), per-suit 0.0–0.05. Applied 2026-09: exo_outfit + svoboda_exo_outfit ×1.5 (physical 0.56→0.84), scientific_outfit («СЕВА») ×1.8 (0.3→0.54, anomaly 0.061→0.11). Existing saves pick it up on next load — outfits are recreated from their sections.

### Run Game in a Window

Clear Sky has no in-game windowed toggle. Edit `Documents/Stalker-STCS/user.ltx` (overwritten by the engine at exit, but it saves the in-memory value, so editing the file sticks): line `rs_fullscreen on` → `off`. Window size = `vid_mode` (e.g. 1920x1080 — near-fullscreen with frame; lower vid_mode there if a smaller window is wanted).

### Enable Sprint in Exoskeletons

Same sections. Set `sprint_allowed = true` (originally `false`).

### Unlock All Mechanic Upgrades

File: `stalkers_upgarde_info.ltx`. In every `*_upgr` section, comment out (prefix with `;`) all `up_sect_* = false` and `up_sect_* = {+info_...}` lines.

### Give Every Mechanic All Items

Same file. Canon source of truth = `[upgraded_inventory]` in `misc/inventory_upgrades.ltx` (the engine's own startup list of upgradeable items — 68 lines: 16 suits + 52 weapons, incl. quest weapons and patch additions like wpn_rg-6/wpn_rpg7/mar_quest_novice_outfit_1); copy those lines verbatim into every mechanic's section. A remembered «43+15» figure or an old snapshot list silently misses patch-added items, so some mechanics end up unable to upgrade part of the arsenal. `*_minigame` w_* sections are service junk — never include them. Mechanics to cover: `mar_csky_tech`, `esc_tech_stalkerbase`, `gar_bandit_fixer`, `gar_digger_fixer`, `val_freedom_fixer`, `agr_duty_base_mechanic`, `agr_stalker_base_mechanic`, `red_forester`, `kat_cs_commander` (+ any NPC you promote to mechanic, e.g. `sakharov`). After the rewrite assert every mechanic section has the same non-comment line count as `[upgraded_inventory]` — unequal counts are how «still can't upgrade X at mechanic Y» slips through.

These nine are the ONLY mechanics that ever existed — vanilla db, SRP and mod bases all ship exactly these sections. A trader without one has NO upgrade UI: Sakharov (Yantar, sells «Сева») never had a section, so «can't upgrade my Seva» at his counter is expected, not a bug. To make any NPC a mechanic, append `[<npc>]` with the same canonical list plus an empty `[<npc>_upgr]` (e.g. `[sakharov]`). The gate is the db script `scripts/inventory_upgrades.script` `can_upgrade_item(item, mechanic)`: false if the mechanic's section carries `he_upgrade_nothing` or lacks the item's name line; `precondition_functor_a` then only checks money when the item's `up_sect_*` line in `<mech>_upgr` is absent/commented.

### Remove `he_upgrade_nothing` (Unblock Forester/Commander)

Same file. Delete the `he_upgrade_nothing` line from `[red_forester]` and `[kat_cs_commander]` sections.

Replace tabs with spaces in `$app_data_root$` line. Use forward slashes (`C:/Users/...`), not backslashes (escape issues in ltx parser). Use full path, not 8.3 short names.

File: `configs/creatures/actor.ltx` (copy from `documents/gamedata/configs/creatures/` if missing). Increase: `run_coef`, `sprint_koef`, `run_back_coef`, `walk_back_coef`, `walk_accel`. Original values are in comments after `;`.

## Pitfalls

- **`physic_strike_wound_immunity` does not match `*_protection` regex.** Handle it separately.
- **Section matching:** `[exo_outfit]` appears as `[exo_outfit]:outfit_base`. Use prefix match.
- **Don't blindly replace `= 0.4`** — it catches `= 0.45` too (military_outfit). Target specific sections.
- **`red_forester_upgr` is empty** — the forester had `he_upgrade_nothing`. Just give him items.
- **GOG version stores config templates in `documents/gamedata/configs/`** — these are reference copies. Real modding goes in `gamedata/configs/`.
- **Sprinting causes health damage.** Symptom: player takes damage + groans when running. Verified 2026-09: the real damage mechanism at BOOSTED speed is NOT power_hit_part — engine code (EntityCondition.cpp) shows power_hit_part only converts incoming HITS into stamina drain, not stamina into health. The actual triggers when running fast: (1) `ph_crash_speed_min`/`ph_crash_speed_max` in `[actor]` — crash/stumble thresholds read by Actor.cpp → `SetCrashSpeeds()`; vanilla 14/30, at run_coef 3+ the actor stumbles off ledges/steps and takes fall damage — raise to ~90/150 to disable stumbling entirely; (2) `max_walk_weight` (actor_condition) — if below carried weight the actor is OVERWEIGHT and sprint hurts: vanilla 60, cheat bases use 1500; (3) `power_hit_part = 0.0` in `[actor_condition]` — still set it (prevents hit→stamina drain coupling).
