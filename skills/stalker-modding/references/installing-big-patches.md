# Installing big gamedata patches (SRP) without losing mods

## What a big patch does
A full-tree patch (Sky Reclamation Project = SRP, the Clear Sky equivalent of ZRP; ModDB `mods/srp`, source `github.com/Decane/SRP`) drops a complete `gamedata/` over the game root. Every file with a matching path is REPLACED — trade files, `character_desc_*.xml`, cheat scripts, `actor.ltx`, the whole `scripts/` tree.

SRP v1.1.4 specifics: gamedata-only (no executable patching); ~1000 files incl. 391 scripts, its own 18 trade files, its own character_desc XML, its own actor.ltx; the readme states a NEW GAME is required (only SRP 1.1.3+ saves are compatible) because script/logic changes clash with saves made on vanilla logic.

## Before installing: snapshot (user requirement — exact file texts must survive)
1. `cd <game>/gamedata && find . -type f -newermt "<install date>" ! -name "*.bak*"` → copy each, preserving paths, into `Documents\Stalker_mods_backup\gamedata_full_copy\`.
2. Copy the idempotent re-apply scripts next to it (`reapply_scripts\`): trade_sell_all.pl, trade_sell_all_fix.pl, bump_stock.pl, npc_money_boost.pl.
3. Write a plain-text `manifest.txt`: one block per mod — files touched, exact change (values!), re-apply method (script vs file copy).
4. Also save vanilla originals of edited files (`*.bak_sellall` etc.) into `orig_vanilla\`.
5. Back up saves (`Documents\Stalker-STCS\savedgames\`) before any patch whose readme demands a new game.

## Re-apply AFTER the patch — scripts on top, not old files
- Trade/money scripts are idempotent (they detect their own `; sell-all stock` / `; *-all mod` markers) and can run on ANY baseline — including the patch's own versions — and can be re-run after a full-file copy.
- Do NOT copy old `trade/*.ltx` or `character_desc_*.xml` back over the patch's files: you would silently discard the patch's fixes to exactly those files. Run the scripts instead.
- Cheat scripts, vehicles, outfit/actor mods have no script form: copy them back from `gamedata_full_copy` (accepting that the patch's versions of those same files are replaced by the user's older ones — that is the point of a cheat).
- Order: unpack patch → `reapply_all.cmd` (runs the 4 scripts) → copy remaining blocks → load the save; on crash either roll gamedata back from the pre-patch backup or start a new game.

## SRP conflict map (what it overwrites, from the v1.1.4 archive)
- `configs/misc/trade/` (18 files) + `trade_generic.ltx` → re-run trade scripts
- `configs/gameplay/character_desc_*.xml` (on disk after install: 13 — MORE than the 8 you boosted, incl. limansk/katacomb/military/stancia_2/generator; count yours) → re-run the money boost over the whole `character_desc_*.xml` glob, never the old file list
- `configs/creatures/actor.ltx`, `m_stalker.ltx`, `game_relations.ltx` → copy user actor mod back
- `scripts/` (391 files: ui_main_menu, ui_si spawner integration may be among them) → copy cheat scripts back
- Optional feature folders (`SweetFX`, `Real Weapon Names`, `User Configuration Patch`, `Alternative Ballistics`, `Improved LuaJIT Library`) — read `SRP v1.1.4 - Optional Features.txt` before choosing.

## If the game crashes right after the install
- A MANUAL (Explorer) copy install can leave a MIXED tree: files the patch does not ship keep whatever was on disk, and a user copying "to finish the job" may pull same-path files from other mod folders (e.g. Desktop mod archives). Symptom: `Can't open section 'up_gr_*'` at save select/load — sibling files disagree (outfit.ltx `upgrades =` paired refs vs o_*.ltx single-letter definitions). Diagnose with md5, NOT file dates: patch archives keep original timestamps (SRP ships 2013–2021 dates) and extractors preserve them, so patch-overwritten files still look old — a date-based read misjudged the whole weapons/upgrade tree as untouched user mods when md5 showed 340/365 configs were the patch's. Run scripts/compare_patch_md5.py <patch.zip> <gamedata/>; every config that MATCHES the zip is patch-owned (even with an old timestamp).
- Run scripts/audit_upgrade_refs.py to list every broken armor/weapon file at once — fix ALL of them in one pass, not just the first crashing section.
- Fix = restore the canonical file from configs.db (uncompressed payload; verify it defines the needed branches first; .bak the bad file). Do NOT guess by copying the crashing file from a mod folder — that is the likely source of the mismatch. Re-run the audit until clean, then load the save.

## Verified re-apply deltas over SRP v1.1.4 (ground truth, 2026-09)
- **Money**: SRP ships its own, LARGER character_desc set — 13 files on disk (incl. limansk/katacomb/military/stancia_2/generator) vs the 8 you boosted; the folder-glob boost pass hit 262 `<money>` tags (was 63). Files without money tags are skipped harmlessly. Never hardcode the old file list.
- **Trade**: SRP restructured every trade file to `#include "trade_template.ltx"`; `[trader]` points at shared sections `[trade_generic_buy]:trade_nothing` / `[trade_generic_sell]:trade_nothing`; the template's `[trade_nothing]` carries the patch's GLOBAL NO TRADE ban list (~112 lines: af_*, ammo, detectors, device_pda, military_outfit...). The buy-all fix pass then reports ONE file (trade_template.ltx) with a large count — clearing a ban in the shared parent unlocks BOTH buy and sell for EVERY trader at once (NPCs also start offering PDAs/detectors/artifacts: consistent with sell-everything, but not buy-only). trade_template.ltx itself has no `[trader]` header (fine); some traders legitimately ship without `buy_supplies` (SRP secret trader has `;buy_supplies` commented — same as the working pre-patch state: leave it).
- **Scripts**: list the patch zip per script before deciding. SRP ships ui_main_menu.script, bind_anomaly_zone.script, sr_no_weapon.script, modules.script; does NOT ship zone_no_weapon/god/ui_teleport/anom/ui_si (md5-verify survivors against the snapshot). SRP ui_main_menu wires btn_spawn to `ui_spawn_dialog.spawn_dialog()` but ships no ui_spawn_dialog.script (dead button) and drops the user's hotkeys → restore the snapshot ui_main_menu.script. Keep patch bind_anomaly_zone.script and sr_no_weapon.script (Decane-fixed; paired with patch modules.script `load_scheme("sr_no_weapon")`). Robust dialog entry = hotkeys in main_menu:OnKeyboard (DIK_Y spawner, DIK_U teleport): db-vanilla ui_mm_main.xml has no btn_spawn element and no gamedata override exists, so button callbacks never fire while hotkeys always do.
- **Mechanics file**: the patch version is NOT vanilla: partial per-mechanic lists (25–52 of the canonical 58) PLUS its own quest-weapon lines (`agr_quest_duty_abakan ; DC260818` style). Re-apply by APPENDING the canonical set into each mechanic while KEEPING the patch's quest lines; red_forester/kat_cs_commander are `he_upgrade_nothing` + empty list → replace the whole body with the canonical set. The ban-comment pass hits both `= false` and `= {+info_...}` forms (153 lines on the SRP file).
- **actor.ltx / outfit.ltx**: patch versions are structurally different (SRP actor.ltx adds `[actor]:common_ph_*` sections; SRP outfit.ltx lacks the mod's commented `#include` blocks) — apply key-by-key value transfer from the snapshot (regex each key, rewrite its value in place, keep every patch line); never whole-file copy-back. Snapshot values are already the boosted ones, so transfer == re-apply.
- **quest_items.ltx**: the patch may COMMENT OUT sections (`;[device_pda_military]:device_pda` with every body line `;`-prefixed) or drop them entirely — those sections leave pSettings and any save/task referencing them FATALs later. Re-add FULL clones from the pre-patch snapshot (they carry the can_trade=true / quest_item=false markers).
- **Parsing the snapshot**: perl-rewritten files can carry `\r\r\n` endings — normalize before regex work; slice section blocks between plain `find('\n[')` positions instead of lookahead section regexes, which silently returned empty bodies on the mixed-EOL snapshot.
- **Upgrade system**: SRP overwrites the whole upgrade generation (item sections w_*.ltx + tree files w_*_up.ltx + o_*.ltx + outfit.ltx `upgrades =` lists) with its own combo-branch trees, and its trees carry 2nd-level branches it never connects (o_exo: 16 up_gr vs 5 listed; w_abakan_up: 12 vs 6) — the player sees «can't install all upgrades / limit». Restoring the user's «full upgrades» mod means copying the WHOLE mod generation back from its source archive (Desktop mod folders — the mtime snapshot does NOT cover old mod files), INCLUDING outfit.ltx from the pre-patch snapshot (it carries the boosted armor values + exo sprint). Then re-verify: (1) every item `upgrades =` ref resolves in the copied tree files; (2) every `upgrade_scheme = u*` value exists as a cell in configs/ui/inventory_upgrade.xml (schemes are XML, not ltx); (3) every name in `[upgraded_inventory]` (misc/inventory_upgrades.ltx) has a section — it VERIFY2-FATALs at startup otherwise (clone missing ones from the base item, `installed_upgrades` commented); (4) no dup sections/CRLF. Full mechanics: references/upgrade-system.md.
- **Per-block verification after each re-apply step**: CRLF intact, no duplicate section header inside one file, `[trader]` fields present where the scheme has them, md5 spot-check of untouched files against the snapshot.
